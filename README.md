# Display Card Manager

管理在**雅虎拍卖 / 煤炉（Mercari）**购入、并在**中国出售**的显卡与整机设备。记录采购与
出售信息、5 类图片/视频（显卡外观、PCB、GPU 核心、GPU-Z、mods 测试），按**交易日期
自动换算日元⇄人民币汇率**，并算出成本与利润。

库存里有两种货，同一张列表里用「类型」列区分：**显卡**是一进一出（一个买价、一个卖价）；
**整机设备**是一进多出（一笔总价买回来，拆成 CPU / 显卡 / 内存 / 硬盘 / 主板 / 电源等
部件分别出售，因此有多个出售价格）。

前后端分离：前端 Vue3 + Element Plus，后端 Python + FastAPI，数据存 **MySQL**，
图片/视频存自建**图床**（[Image_hosting](../Image_hosting)）。界面风格与
[FreeMarket_Manager](../FreeMarket_Manager) 一致（深色主题，中/日/英三语）。

## 技术栈

| 层 | 选型 |
|----|------|
| 前端 | Vue 3、Element Plus、Pinia、vue-router（hash）、vue-i18n、ECharts、axios |
| 后端 | FastAPI、uvicorn、PyMySQL（原生 SQL，无 ORM）、PyJWT、bcrypt、requests |
| 数据库 | MySQL 8（utf8mb4） |
| 运行环境 | conda 环境 `displayCard`（Python 3.12） |
| 文件存储 | Image_hosting 图床（`/api/v1` Bearer Token） |
| 汇率源 | 欧洲央行（Frankfurter），按交易日期取历史牌价，本地缓存 |

## 首次运行

### 1. 准备 conda 环境（已存在可跳过）

```powershell
conda create -n displayCard python=3.12
conda activate displayCard
pip install -r backend/requirements.txt
```

### 2. 配置 MySQL 连接

编辑项目根目录的 `conf.ini`，`[mysql]` 段至少填对 `host` / `user` / `password`：

```ini
[mysql]
host = 127.0.0.1
port = 3306
user = your_user
password = your_password
database = display_card
charset = utf8mb4

[server]
host = 0.0.0.0
port = 9910
```

库 `display_card` 不存在时，若账号有建库权限会自动创建；否则请先手动建一个空库：

```sql
CREATE DATABASE display_card CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

> 每一项都能用环境变量覆盖（如 `DISPLAYCARD_MYSQL_PASSWORD`），方便打包后在不同机器
> 部署时不改文件。

### 3. 启动

双击 `start.bat`，或分别：

```powershell
# 后端
conda activate displayCard
cd backend
python main.py            # 监听 9910

# 前端（另开一个终端）
cd webside
npm install
npm run dev               # 监听 9911
```

浏览器打开 **http://localhost:9911**。首次登录 `admin` / `admin`，登录后请立即在
「系统配置 → 账号」中改密码。

### 4. 配置图床

到「系统配置 → 图床」填写：

- **后端连接地址**：本程序连图床用，通常内网直连，如 `http://127.0.0.1:9990`
- **公开访问地址**：浏览器打开图片用，留空则同上
- **项目标识**：在图床里为本项目创建的 project slug，如 `displaycard`
- **API Token**：图床项目详情里复制

保存后点「测试连接」验证。

> **图床需支持视频**：本项目要上传 mp4 等视频，请确认图床端已放开视频扩展名并对视频跳过
> PIL 图片校验（图床默认只认 8 种图片格式）。

## 核心业务约定

### 汇率

- 汇率一经取到就**快照写死在卡片行里**（`purchase_fx_rate` / `sale_fx_rate`），之后不再
  重算——已发生交易的盈亏不应随每日汇率波动。
- 周末 / 节假日无牌价时**自动回退**到不晚于该日的最近一个发布日，并记录实际牌价日。
- 需要精确成交价时可在卡片上**手工填汇率**（`fx_manual=1`），此后自动刷新跳过该卡。
- ECB 是参考中间价，不等于实际换汇成交价。

### 金额与币种

每个金额字段自带币种下拉（日元 / 人民币）。折算成人民币时：

| 金额 | 用哪个汇率 |
|------|-----------|
| 购入价、国际运费 | 购入日汇率 |
| 国内运费、出售价 | 出售日汇率 |

**利润 = 出售价 −（购入价 + 国际运费 + 国内运费）**，全部折成人民币。任何一项因缺汇率
折不出来时，含它的合计返回空而非按 0 计——避免算出一个偏高的假利润。

### 资金池

日常做法往往是「先换一笔日元放在日本的账户里，再陆续用它买货」。这时一件货的真实人民
币成本取决于**买它的钱是哪一批换进来的**，而不是买它那天的市场牌价——同一天买的两张
卡，如果吃的是不同批次的钱，成本就不一样。显卡与整机都能挂到池子上。

- **注资**：每次换汇进池记一笔，带自己那天的汇率（自动取牌价，或手填真实换汇价）。
- **扣款**：显卡或整机上打开「从资金池扣除」后，它的**日元**购入价与国际运费会在池里生成
  对应扣款（一卡一类一条 / 一机一类一条）；与两者都无关的池内支出（手续费等）可在资金池
  页面手工记。`fund_draws` 上的 `card_id` / `device_id` 两列互斥，标明这笔钱归谁。
- **FIFO 分摊**：一笔扣款按注资日期先进先出地吃掉若干批次，**每段各按该批次自己的汇率
  折算再相加**。跨多个注资时间的支出因此会得到分段成本，卡片详情里能看到每一段。
- 扣款只能吃 `注资日 ≤ 支出日` 的批次（还没进池的钱花不出去）。吃不满的部分记为
  **余额不足**，按当日市场牌价折算并给出警告，提示去补录注资。
- 分摊是**全量派生数据**：改注资、改金额、删卡/删整机之后整体重算（`funds.rebuild()`），
  结果回写到归属行上（`cards` / `devices` 的 `pool_purchase_cny` / `pool_intl_cny` /
  `pool_fx_rate`，两张表同名同义），列表与统计直接取用，不必逐行查明细。
- 走资金池的记录，采购侧成本**不再使用** `purchase_fx_rate`；出售侧不受影响（卖出收的是
  人民币，仍走出售日汇率）。

### 整机设备（一进多出）

整机是**一笔总价**买回来的，拆开按件卖，所以「购入价」只有一个、「出售价」有多个。数据
因此分成两张表：`devices` 放采购侧（总价、国际运费、购入日汇率快照），`device_parts` 放
出售侧，一台设备多行，每行一个部件、一个售价。

- **内存 / 硬盘可以有多条**：它们是 `device_parts` 里的多行，不是设备表上的固定字段——
  写死几个字段就装不下第三条内存。同规格的多件（如 2 条 16G）可以合成一行填数量。
- **汇率**：购入价与国际运费跟着设备的购入日；每个部件的售价与国内运费跟着**该部件自己
  的出售日**——部件是分不同日子卖掉的，共用一个出售汇率会算错。
- **利润** = Σ部件售价 −（购入总价 + 国际运费 + Σ部件国内运费）。部件没卖完时这个数字
  只是「目前收回了多少」，列表与表单里会标成「出售中」，全部卖出后才是最终盈亏。
- **成本不往部件上摊**：只有一个总价，按售价比例摊还是按市场价摊能差出一倍，都是假精度。
  想看单件贡献就看它的售价与净收入（售价 − 国内运费）。
- 表单与显卡一样是**实时自动保存**的，没有保存按钮；部件数组每次整体提交，后端覆盖式
  写入（部件行没有任何外部引用指向它，行 id 不需要稳定）。
- 表单默认摆出 **CPU / 显卡 / 内存 / 硬盘 / 主板 / 电源** 六个槽位（一台机器几乎必然有
  这些），按实际情况填即可；**一个字都没填的槽位不会保存**，所以它只是录入模板，不会变成
  一堆空部件（否则部件数会永远显示成 0/6、「已清算」永远为假）。内存、硬盘有多条时用
  「快捷添加」再加一行。
- 各类部件的录入口径不同，写在 `webside/src/constants/parts.js` 里：CPU 的品牌只有
  Intel / AMD（不允许现场新建），显卡的品牌与型号取系统里的字典，「规格」那一栏各类型
  的标题和候选值也各不相同（显存 / 容量+接口 / 功率 / 芯片组）。给候选值是为了让同一样
  东西每次都写成同一种样子——不然几台机器之后同一个 2TB 固态会有三种写法，之后想按容量
  统计就全乱了。清单不是白名单：除 CPU 外都能现场输入清单以外的值。
- **资金池**与显卡同一套：表单上打开「从资金池扣除」后，这台机器的日元购入价与国际运费
  会在池里生成扣款，成本改按被吃掉的注资批次分段折算。整机没有独立详情页，所以分段明细
  直接显示在编辑弹窗里（也能在资金池页面的「使用明细」中看到）。

### 库存合并列表

显卡与整机在**同一张列表**里，靠「类型」列区分，筛选 / 排序 / 分页由 `api/inventory_api.py`
统一做：它把两种货规范化成同一种行（编号、名称、状态、日期、成本、收入、盈亏）再合并，
两者的行样式因此完全一致。排序和分页在 Python 侧完成——成本与利润不是数据库列，而是按
汇率快照算出来的，想在 SQL 里按利润排序就得把整套换算逻辑再写一遍，两份实现迟早对不上。

整机那一行可以展开出**二级行**，每个部件一行，用的是同一套列（类型列显示 CPU / 内存…，
出售日期、已收回照常）。部件被规范化成和顶层行同样的形状（`_part_row`），所以前端不必为
二级行另写一张表；不适用的列给 None 显示成「—」：部件没有购入日，也没有单件成本——整机是
一口价买的，总价不往部件上摊。二级行的「已收回」加起来正好等于整机那一行。

### 状态流转

`已购入 → 待测试 → 测试通过 / 测试不通过 → 回国中 → 转寄中 → 已签收 → 已打款`

「已签收」「已打款」是中国买家的动作；走到「已打款」这笔生意才算完。每次状态变更都记
一条流转日志，可在卡片详情里追溯（例如卡在海关卡了多久）。
